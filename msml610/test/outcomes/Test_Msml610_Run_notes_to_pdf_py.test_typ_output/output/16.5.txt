==== Why Memory and Planning Deserve Their Own Lesson
<why-memory-and-planning-deserve-their-own-lesson>
- #text(fill: red, weight: "bold")[Motivation]: Lesson 16.4 studied
  reasoning as a #emph[single] chain of tokens inside one episode
  - Real agents run #emph[many] episodes, over #emph[long] horizons,
    revisiting the #emph[same] world
  - A reasoner that forgets everything between episodes cannot improve,
    avoid repeated mistakes, or act on facts learned yesterday
- #text(fill: green, weight: "bold")[Question]: Lesson 16.3 closed by
  asking how reasoning, memory, and planning combine to fix long-horizon
  failures
  - Lesson 16.4 closed by asking how memory and planning extend
    single-shot reasoning across a full loop
  - This lesson answers both
- #text(fill: blue, weight: "bold")[Key idea]: memory extends reasoning
  #emph[across time];, planning extends it #emph[across actions]

==== What Do We Mean by Memory and Planning?
<what-do-we-mean-by-memory-and-planning>
- #text(fill: red, weight: "bold")[Definition]: #emph[memory] is the
  mechanism an agent uses to carry information forward, either within an
  episode or across episodes

- #text(fill: green, weight: "bold")[Definition]: #emph[planning] is
  deciding a sequence of actions #emph[before] (or while) executing
  them, rather than choosing one action at a time reactively

  - As introduced in Lesson 16.1, planning is the step that picks the
    next action; here we ask how far ahead that step can look

- #text(fill: blue, weight: "bold")[Key idea]: both extend the
  perceive-plan-act loop (Lesson 16.1) along a different axis

  - Memory: what persists
  - Planning: how far ahead the agent looks before acting

==== Working Memory: The Context Window as a Scratchpad
<working-memory-the-context-window-as-a-scratchpad>
- #text(fill: red, weight: "bold")[Definition]: #emph[working memory] is
  everything the model can attend to in the current forward pass, i.e.,
  the tokens in its context window
  - As we saw in Lesson 16.2, this includes the prompt, the CoT
    scratchpad, and the KV-cache of past tokens
- #text(fill: green, weight: "bold")[Properties]:
  - #emph[Fast];: no retrieval step, every token is directly attendable
  - #emph[Bounded];: capped by the context window size
  - #emph[Volatile];: discarded when the episode ends, unless copied
    elsewhere
- #text(fill: blue, weight: "bold")[Key idea]: CoT (Lesson 16.4) is
  reasoning conducted #emph[entirely] in working memory
  - This is why long reasoning chains are expensive: they consume the
    same finite resource as everything else in the prompt

==== Long-Term Memory: Beyond What Fits in Context
<long-term-memory-beyond-what-fits-in-context>
- #text(fill: red, weight: "bold")[Problem]: an agent that runs for
  days, or across many episodes, accumulates far more information than
  any context window can hold

- #text(fill: green, weight: "bold")[Definition]: #emph[long-term
  memory] is information that persists #emph[outside] the context window
  and is brought in only when needed

- Two ways to realize long-term memory

  + #emph[External];: store facts in a database or knowledge graph,
    retrieve into the context window on demand (e.g., HippoRAG)
  + #emph[Parametric];: bake the facts and the reasoning over them
    directly into the model's weights via training (e.g., grokking)

- #text(fill: blue, weight: "bold")[Key idea]: the two are not
  competitors; a production agent typically uses both

==== Working vs.~Long-Term Memory: Comparison
<working-vs.-long-term-memory-comparison>
#styled-table(
  headers: ("Property", "Working memory", "Long-term memory"),
  rows: (
    ("Location", "Context window", "External store or weights"),
    ("Capacity", "Fixed, small", "Effectively unbounded"),
    ("Access cost", "Free (already attended)", "Retrieval or recall step"),
    ("Persistence", "One episode", "Across episodes"),
    ("Failure mode", "Overflow, truncation", "Retrieval miss, stale facts"),

)
- #text(fill: red, weight: "bold")[Key idea]: moving information from
  long-term to working memory is exactly #emph[retrieval];, the
  bottleneck the next two sections address

==== The Core Problem: Retrieval, Not Storage
<the-core-problem-retrieval-not-storage>
- #text(fill: red, weight: "bold")[Question]: storing facts is easy (a
  database scales); what is hard?

- #text(fill: orange, weight: "bold")[Problem]: #emph[retrieval];,
  choosing the small subset of stored facts that answers the current
  query

  - #text(fill: green, weight: "bold")[Single-hop]: the query directly
    mentions the needed fact; nearest- neighbor search over embeddings
    usually works
  - #text(fill: teal, weight: "bold")[Multi-hop]: the answer requires
    #emph[chaining] facts that were never stated together in any single
    passage
  - Standard retrieval-augmented generation (RAG) is built for the
    single-hop case

- #text(fill: rgb("#00FFFF"), weight: "bold")[Key idea]: multi-hop
  retrieval needs #emph[structure] across facts, not just similarity
  between a query and one passage

  - This is exactly the gap HippoRAG targets

==== Problem: Why Standard RAG Struggles with Multi-Hop Facts
<problem-why-standard-rag-struggles-with-multi-hop-facts>
- #text(fill: red, weight: "bold")[Recap]: standard RAG embeds the
  query, retrieves the top-$k$ most similar passages, and pastes them
  into the context window

- #text(fill: green, weight: "bold")[Problem]: a multi-hop question
  (#emph["Where did the director of the film from \[studio\] X get their
  degree?"];) needs facts from #emph[several] passages that individually
  look unrelated to the query

  - Similarity search on the query embedding misses the second and third
    hop
  - Iterative methods (retrieve, reason, retrieve again) fix this but
    pay for #emph[multiple] LLM calls per query

- #text(fill: blue, weight: "bold")[Question] (Gutiérrez et al., 2024):
  can a single retrieval pass integrate information the way a brain
  consolidates experiences into associative memory?

==== Biological Inspiration: The Hippocampal Indexing Theory
<biological-inspiration-the-hippocampal-indexing-theory>
- #text(fill: red, weight: "bold")[Fact]: in mammalian brains, the
  #emph[hippocampus] and #emph[neocortex] play distinct memory roles

  - The neocortex stores rich, slowly-consolidated knowledge
  - The hippocampus builds a fast, sparse #emph[index] of associations
    between pieces of that knowledge, without duplicating the knowledge
    itself

- #text(fill: green, weight: "bold")[Key idea]: the hippocampus does not
  store facts, it stores #emph[pointers between] facts, which is what
  makes multi-hop association fast

- #text(fill: blue, weight: "bold")[Mapping to LLMs]:

  - Neocortex $arrow.r$ the LLM's parametric knowledge and the raw text
    corpus
  - Hippocampal index $arrow.r$ a knowledge graph over entities and
    relations
  - Pattern separation and completion $arrow.r$ graph retrieval that
    jumps across linked entities

==== HippoRAG: Architecture Overview
<hipporag-architecture-overview>

  - Three stages

    + #emph[Online];: retrieve via personalized PageRank over that graph

- #text(fill: blue, weight: "bold")[Key idea]: separating #emph[offline]

==== Step 1: Offline Indexing via Open Information Extraction
<step-1-offline-indexing-via-open-information-extraction>
- #text(fill: red, weight: "bold")[Definition]: #emph[open information
  extraction] (open IE) extracts
  #text(fill: blue)[`(subject, relation, object)`] triples from text
  without a fixed schema
  - #emph[Example];: #emph["Marie Curie discovered radium"] $arrow.r$
    `(Marie Curie, discovered, radium)`
- #text(fill: green, weight: "bold")[Algorithm]:
  + Run an LLM over each passage to extract triples
  + Each triple contributes two #emph[nodes] (subject, object) and one
    labeled #emph[edge] (relation)
  + Merge nodes referring to the same entity across passages (synonymy)
- #text(fill: blue, weight: "bold")[Key idea]: this is done #emph[once];,
  offline, over the whole corpus
  - The cost is amortized across all future queries, unlike iterative
    retrieval which repeats LLM calls per query

==== Step 2: Building the Knowledge Graph
<step-2-building-the-knowledge-graph>
- #text(fill: red, weight: "bold")[Definition]: the extracted triples
  form a graph $G = \( V \, E \)$
  - $V$: entities mentioned anywhere in the corpus
  - $E$: relations between them, plus a link from each entity back to
    every passage that mentions it
- #text(fill: green, weight: "bold")[Key idea]: this graph is the
  #emph[hippocampal index]
  - It does not replace the corpus (the neocortex); it stores #emph[how]
    pieces of the corpus relate
  - Two entities that never co-occur in one passage can still be
    #emph[close] in the graph if a chain of other entities connects them
- #text(fill: blue, weight: "bold")[Example]: #emph["Director"] and
  #emph["University"] never appear in the same sentence, but both
  connect through #emph["Film"] and #emph["Studio"] nodes

==== Step 3: Online Retrieval via Personalized PageRank
<step-3-online-retrieval-via-personalized-pagerank>
- #text(fill: red, weight: "bold")[Problem]: given a query, which graph
  nodes are relevant?

- #text(fill: green, weight: "bold")[Solution]: run #emph[personalized
  PageRank] (PPR), seeded at the entities mentioned in the query
  $ upright(bold(p)) = \( 1 - alpha \) thin upright(bold(q)) + alpha thin upright(bold(W)) upright(bold(p)) $

  - $upright(bold(q))$: the #emph[reset] vector, concentrated on query
    entities
  - $upright(bold(W))$: the graph's transition matrix
  - $alpha$: damping factor controlling how far probability mass spreads

- #text(fill: blue, weight: "bold")[Algorithm]:

  + Extract entities from the query with the same open IE step
  + Seed PPR at those entities
  + Rank passages by the PPR mass on the entities they mention
  + Return the top-ranked passages to the LLM

==== HippoRAG: Worked Example
<hipporag-worked-example>
- #text(fill: red, weight: "bold")[Problem]: #emph["Where did the
  director of \[Film\] study?"]

- #text(fill: green, weight: "bold")[Solution] (single PPR pass)

  + Seed: the #text(fill: blue)[`[Film]`] entity node
  + PPR spreads mass along #text(fill: blue)[`[Film]`] $arrow.r$
    #text(fill: blue)[`directed_by`] $arrow.r$
    #text(fill: blue)[`[Director]`]
  + Mass continues along #text(fill: blue)[`[Director]`] $arrow.r$
    #text(fill: blue)[`studied_at`] $arrow.r$
    #text(fill: blue)[`[University]`]
  + Passages mentioning #text(fill: blue)[`[University]`] rank highly,
    even though no single passage mentions #text(fill: blue)[`[Film]`]
    and #text(fill: blue)[`[University]`] together

- #text(fill: blue, weight: "bold")[Interpretation]: one graph walk
  implicitly performs the #emph[multi-hop chain] that standard RAG would
  need several retrieval-and-reason rounds to find

==== HippoRAG: Results and Efficiency
<hipporag-results-and-efficiency>
- #text(fill: red, weight: "bold")[Findings] (Gutiérrez et al., 2024),
  on multi-hop QA benchmarks:
  - Outperforms standard RAG retrieval by up to $20 %$ on multi-hop
    questions
  - Matches iterative retrieval-and-reason methods (e.g., IRCoT) in
    accuracy
  - Does so with a #emph[single] retrieval pass: $10$-$30 times$ cheaper
    and $6$-$13 times$ faster than the iterative alternative
  - Combining HippoRAG with iterative reasoning yields further gains,
    i.e., the two are complementary, not substitutes
- #text(fill: blue, weight: "bold")[Key idea]: structuring long-term
  memory as a graph, indexed the way a hippocampus indexes experience,
  buys most of the accuracy of expensive multi-hop search at a fraction
  of the cost

==== Problem: Can Reasoning Live Inside the Weights?
<problem-can-reasoning-live-inside-the-weights>
- #text(fill: red, weight: "bold")[Recap]: HippoRAG keeps facts
  #emph[external] and retrieves them on demand

- #text(fill: green, weight: "bold")[Question]: could a model instead
  learn to #emph[chain] facts internally, so that a multi-hop answer
  comes out of a single forward pass, with no retrieval step at all?

  - This would be reasoning stored as #emph[parametric long-term memory]

- #text(fill: blue, weight: "bold")[Motivation]: Lesson 16.4 showed a
  forward pass is fixed-depth and needs CoT tokens for serial reasoning

  - Could #emph[training];, rather than more tokens, give a model the
    equivalent of a pre-computed reasoning chain?

==== What Is Grokking?
<what-is-grokking>
- Aka:

  - "Delayed generalization"

- #text(fill: red, weight: "bold")[Definition]: #emph[grokking] is a
  training phenomenon where a model first #emph[memorizes] the training
  set (near-zero training loss, poor test accuracy), then, after
  continuing to train far past that point, suddenly #emph[generalizes]
  (test accuracy jumps to near-perfect)

- #text(fill: blue, weight: "bold")[Key idea]: the useful behavior is
  hidden #emph[after] the point where training loss looks converged

  - Stopping early, the usual practice, would discard exactly the phase
    where generalization emerges

==== Experimental Setup: Composition vs.~Comparison
<experimental-setup-composition-vs.-comparison>
- #text(fill: red, weight: "bold")[Setup] (Wang et al., 2024): train a
  transformer on synthetic facts designed so the test set requires
  #emph[combining] facts never seen combined during training

- Two reasoning types tested

  - #text(fill: green, weight: "bold")[Composition]: infer $a arrow.r c$
    from $a arrow.r b$ and $b arrow.r c$ (chain facts together)
  - #text(fill: blue, weight: "bold")[Comparison]: infer a relation
    between $a$ and $b$ from separately known attributes of $a$ and of
    $b$

- #text(fill: rgb("#8B00FF"), weight: "bold")[Key variable]: the
  #emph[ratio] of atomic facts (directly stated) to inferred facts
  (requiring composition or comparison) in the training data

  - This ratio controls whether and how fast grokking occurs

==== Finding: Composition Fails to Generalize
<finding-composition-fails-to-generalize>
- #text(fill: red, weight: "bold")[Finding] (Wang et al., 2024): on
  composition, grokked transformers reach near-perfect accuracy on
  in-distribution (ID) test facts
  - But accuracy on out-of-distribution (OOD) composition facts, i.e.,
    chains using entities in combinations never seen even indirectly,
    stays low
- #text(fill: blue, weight: "bold")[Interpretation]: the model learns a
  #emph[lookup-like] shortcut for the specific chains it was exposed to,
  not a general chaining #emph[procedure]
  - Systematic generalization, applying the same rule to genuinely new
    combinations, does not emerge for composition

==== Finding: Comparison Generalizes
<finding-comparison-generalizes>
- #text(fill: red, weight: "bold")[Finding] (Wang et al., 2024): on
  comparison, grokked transformers generalize to OOD test facts as well
  as ID ones

- #text(fill: green, weight: "bold")[Contrast with composition]:

#styled-table(
  headers: ("Task", "ID accuracy", "OOD accuracy"),
  rows: (
    ("Composition", "Near-perfect", "Low"),
    ("Comparison", "Near-perfect", "Near-perfect"),
  ),
)
- #text(fill: blue, weight: "bold")[Key idea]: grokking is not a single
  uniform capability
  - The same training recipe produces systematic generalization for one
    reasoning type and shortcut memorization for another

==== Why the Difference? Generalizing vs.~Memorizing Circuits
<why-the-difference-generalizing-vs.-memorizing-circuits>
- #text(fill: red, weight: "bold")[Question]: what inside the network
  explains the gap?

- #text(fill: green, weight: "bold")[Interpretation] (Wang et al.,
  2024): grokking forms two competing kinds of internal circuits

  - A #emph[memorizing] circuit that stores training examples directly
  - A #emph[generalizing] circuit that implements a reusable rule

- #text(fill: blue, weight: "bold")[Key idea]: which circuit dominates
  depends on which is more #emph[parameter-efficient] for that task

  - Comparison admits a compact generalizing circuit that outcompetes
    memorization once training continues long enough
  - Composition's generalizing circuit is comparatively less efficient,
    so memorization keeps winning even after prolonged training

==== Grokked Transformers vs.~Frontier Models
<grokked-transformers-vs.-frontier-models>
- #text(fill: red, weight: "bold")[Finding] (Wang et al., 2024): on
  complex composition and comparison reasoning tasks built from their
  synthetic facts, fully grokked (small, task-specific) transformers
  achieve near-perfect accuracy where
  #text(fill: green, weight: "bold")[GPT-4-Turbo] and
  #text(fill: blue, weight: "bold")[Gemini-1.5-Pro], prompted with the
  same facts in context, fail substantially

- #text(fill: rgb("#8B00FF"), weight: "bold")[Interpretation]: this is
  not a claim that grokked models are smarter in general

  - It shows that reasoning #emph[compiled into weights] over a fixed
    body of facts can outperform reasoning #emph[read off] the same
    facts placed in a context window, at least on this evaluation

==== Implication: Parametric Memory as Implicit Long-Term Memory
<implication-parametric-memory-as-implicit-long-term-memory>
- #text(fill: red, weight: "bold")[Key idea]: grokking demonstrates a
  #emph[second] route to long-term memory, complementary to HippoRAG's
  external graph
  - HippoRAG: facts stay external, retrieved into working memory per
    query
  - Grokking: facts (and some reasoning over them) are absorbed into the
    weights, available with no retrieval step
- #text(fill: green, weight: "bold")[Limitations]:
  - Grokking needs extensive training well past apparent convergence,
    i.e., it is not a knob available at inference time
  - Generalization is #emph[task-dependent] (comparison, not
    composition)
  - Updating parametric memory means re-training, unlike appending a
    document to a retrieval index
- #text(fill: blue, weight: "bold")[Open question]: how do we get the
  update-ability of external memory with the low latency of parametric
  memory?

==== Problem: Reactive Agents and the Cost of Search
<problem-reactive-agents-and-the-cost-of-search>
- #text(fill: red, weight: "bold")[Recap]: ReAct-style agents (Lesson
  16.3) choose one action, observe the real result, then choose the next
  - This is #emph[reactive];: every candidate action is tried for real
    before its outcome is known
- #text(fill: green, weight: "bold")[Problem]: on the web, many actions
  are #emph[irreversible] (submit an order, delete a file, send a
  message)
  - Test-time tree search (Lesson 16.4's Tree-of-Thought, applied to
    actions) would try and backtrack through several candidates, but
    backtracking is unavailable once a real action fires
  - Trying actions on the live web is also slow and can have side
    effects
- #text(fill: blue, weight: "bold")[Question] (Gu et al., 2024): can an
  agent evaluate candidate actions #emph[without] executing them for
  real?

==== Solution: An LLM as a World Model
<solution-an-llm-as-a-world-model>
- #text(fill: red, weight: "bold")[Definition]: a #emph[world model]
  predicts the next state (or observation) that would result from taking
  an action in a given state, without actually taking it
  $ hat(s)_(t + 1) = M \( s_t \, a_t \) $

- #text(fill: green, weight: "bold")[Key idea]: if an LLM can play the
  role of $M$, an agent can #emph[simulate] several candidate actions
  internally, compare the imagined outcomes, and only execute the best
  one for real

  - This turns planning into search over #emph[imagined] trajectories,
    not real ones, restoring the backtracking that irreversibility
    otherwise forbids

- #text(fill: blue, weight: "bold")[Question]: is a generic LLM already
  an implicit world model of the web, or does it need to be trained for
  this?

==== Training the World Model: Predicting State Transitions
<training-the-world-model-predicting-state-transitions>
- #text(fill: red, weight: "bold")[Solution] (Gu et al., 2024):
  fine-tune an LLM (#emph[Dreamer-7B];) on a synthesized dataset of
  #text(fill: blue)[`(state, action) -> next state`] transitions
  collected from web interactions

- #text(fill: green, weight: "bold")[Algorithm] (data synthesis
  pipeline)

  + Collect trajectories of
    #text(fill: blue)[`(observation, action, next observation)`] from
    web environments
  + Convert raw HTML/DOM observations into a compact textual state
    representation
  + Train the model to predict the #emph[next] textual state given the
    current state and a candidate action

- #text(fill: blue, weight: "bold")[Key idea]: this is a specialized,
  smaller model, not the same LLM doing the acting

  - Separating the #emph[actor] from the #emph[simulator] keeps each
    component focused

==== WebDreamer: Simulate Before You Act
<webdreamer-simulate-before-you-act>
#grid(

  - #text(fill: red, weight: "bold")[Algorithm] (#emph[WebDreamer];):
    + At each step, propose $k$ candidate actions
    + For each candidate, ask the world model to #emph[imagine] the
      resulting state
    + Score each imagined state against the task goal
    + Execute only the highest-scoring candidate #emph[for real]

    in #emph[imagination]
    - The real environment sees exactly one action per step, so
      irreversibility is no longer a problem

==== WebDreamer: Efficiency and Real-World Results
<webdreamer-efficiency-and-real-world-results>
- #text(fill: red, weight: "bold")[Findings] (Gu et al., 2024):
  - $4$-$5 times$ more efficient than test-time tree search over the
    real environment on VisualWebArena, at competitive accuracy
  - Effective on #emph[sandbox] benchmarks (e.g., WebArena-style tasks)
    and on #emph[real];, live websites (Online-Mind2Web, Mind2Web-Live),
    where an actual tree search would risk real side effects
  - The specialized world model, Dreamer-7B, reaches simulation quality
    comparable to prompting #text(fill: green, weight: "bold")[GPT-4o]
    directly for the same predictions, at much lower cost
- #text(fill: blue, weight: "bold")[Key idea]: a modest, purpose-trained
  world model is enough to unlock search-quality planning in an
  environment where real search is unsafe

==== Reasoning, Memory, and Planning: The Full Loop
<reasoning-memory-and-planning-the-full-loop>
- #text(fill: red, weight: "bold")[Key idea]: the three pieces of this
  lesson compose into one control loop

- #text(fill: green, weight: "bold")[Putting it together]:

  - #emph[Reasoning] (Lesson 16.4) decides what to do with the facts in
    working memory right now
  - #emph[Long-term memory] (HippoRAG, grokking) supplies facts that do
    not fit, or were never placed, in the context window
  - #emph[Planning with a world model] (WebDreamer) lets the agent
    evaluate the consequences of an action before committing to it,
    using imagined rather than real rollouts

- #text(fill: blue, weight: "bold")[Example]: an enterprise agent
  retrieves policy facts via a HippoRAG-style graph, reasons over them
  with CoT, and simulates a risky action with a world model before
  executing it

==== Reasoning, Memory, and Planning: Summary and Open Questions
<reasoning-memory-and-planning-summary-and-open-questions>
- #text(fill: red, weight: "bold")[Key takeaways]:
  - #emph[Working memory] (the context window) is fast but bounded;
    #emph[long-term memory] persists beyond it, either #emph[externally]
    (HippoRAG) or #emph[parametrically] (grokking)
  - #emph[HippoRAG] indexes a corpus as a knowledge graph, modeled on
    hippocampal indexing theory, and answers multi-hop queries with one
    personalized PageRank pass, matching iterative retrieval at a
    fraction of the cost
  - #emph[Grokking] shows reasoning can be compiled into weights through
    extended training, but generalization is task-dependent: it emerges
    for comparison, not composition
  - #emph[World models] let an agent simulate candidate actions before
    acting, restoring search in environments (like the web) where real
    actions are irreversible
  - #emph[WebDreamer] operationalizes this with a trained world model,
    gaining $4$-$5 times$ efficiency over live tree search
- #text(fill: blue, weight: "bold")[Open questions]:
  - Can external and parametric long-term memory be combined into a
    single update-able, low-latency system?
  - How accurate must a world model be before simulated search becomes
    unreliable, and how would an agent know?
  - How do these mechanisms trade off against the inference-time
    techniques of Lesson 16.6?
