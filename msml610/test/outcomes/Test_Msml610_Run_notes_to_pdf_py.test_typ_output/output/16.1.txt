==== From Language Models to Agents
<from-language-models-to-agents>
- #text(fill: red, weight: "bold")[Motivation]: a model that only
  predicts the next token cannot, by itself, book a flight, fix a bug,
  or run an experiment

  - Chat interfaces answer questions but the user still does all the
    acting
  - Many valuable tasks require taking #emph[steps in the world];, not
    just producing text

- #text(fill: green, weight: "bold")[Question]: what to add to a
  language model so that it can reliably get things done, not just
  describe what should be done?

- #text(fill: blue, weight: "bold")[Key idea]:

  - Turn the model into the controller of a loop that observes, decides,
    and acts, repeatedly, until a goal is reached
  - This loop is what we call an #emph[agent]

==== The Limits of Pure Text Generation
<the-limits-of-pure-text-generation>
- #text(fill: red, weight: "bold")[Problem]: a standalone LLM is a
  stateless function from text to text
  - No persistent notion of the external world
  - No way to verify whether its claims are true
  - No mechanism to change the state of anything outside the
    conversation
  - You can't "just prompt better"
- #text(fill: green, weight: "bold")[Cons]:
  - Hallucinated facts cannot be corrected by the model itself
  - Multi-step tasks (e.g., #emph["refactor this repo and run the
    tests"];) exceed what a single forward pass can verify
  - No feedback signal tells the model whether its last step worked
- #text(fill: blue, weight: "bold")[Example]: asking a chatbot to
  #emph["deploy this code and tell me if it works"] only produces a
  plausible-sounding answer, not a verified outcome

==== What Makes a System "Agentic"?
<what-makes-a-system-agentic>
- #text(fill: red, weight: "bold")[Definition]: an #emph[agentic AI] is
  a system that:
  - Perceives its environment,
  - Decides on actions toward a goal
  - Executes those actions
  - Possibly over many steps, with limited human supervision
- Aka:
  - "AI agent"
  - "Autonomous agent"
  - "LLM agent" (when the controller is a large language model)
- #text(fill: green, weight: "bold")[Three necessary ingredients]:
  + A #emph[goal] the system is pursuing
  + A way to #emph[act] on an environment (tools, APIs, actuators)
  + A way to #emph[observe] the effect of its actions and adjust
- #text(fill: blue, weight: "bold")[Remark]: "agentic" is a spectrum,
  not a binary property

==== Chatbots: Definition
<chatbots-definition>
- #text(fill: red, weight: "bold")[Definition]: a #emph[chatbot] is a
  conversational system that maps a dialogue history to a text response

- #text(fill: green, weight: "bold")[Goal]: produce a helpful, coherent
  reply

  - The conversation #emph[is] the output: nothing outside the chat
    window changes as a direct result

- #text(fill: blue, weight: "bold")[Example]: a customer-support chatbot
  that answers FAQs by retrieving and paraphrasing documentation

  - It can #emph[describe] how to reset a password
  - It cannot #emph[reset] the password itself

==== Agents: Definition
<agents-definition>
- #text(fill: red, weight: "bold")[Definition]: an #emph[agent] is a
  system that maps a goal and a stream of observations to a sequence of
  #emph[actions] that change the state of an environment
  - The conversation, if any, is one channel among several (the others
    being tool calls, API responses, sensor readings)
- #text(fill: blue, weight: "bold")[Example]: a coding agent that reads
  an issue, edits files, runs the test suite, and iterates until tests
  pass
  - The repository's state, not just the chat transcript, is the output

==== Agents vs.~Chatbots: Key Differences
<agents-vs.-chatbots-key-differences>
#grid(
  columns: (48%, 48%),
  gutter: 0.5em,
  [
  #text(fill: red, weight: "bold")[Chatbot]
  
  - Output: text only
  - State: conversation history
  - Loop: single turn $arrow.r$ response
  - Failure mode: wrong answer
  ],
  [
  #text(fill: green, weight: "bold")[Agent]
  
  - Output: text and side effects (files, API calls, transactions)
  - State: environment state + memory
  - Loop: perceive $arrow.r$ plan $arrow.r$ act, repeated
  - Failure mode: wrong answer #emph[or] wrong action taken
  ]
)
- #text(fill: blue, weight: "bold")[Key idea]:
  - Every agent can act like a chatbot (e.g., explain its plan)
  - A chatbot becomes an agent only once it is given tools and a
    feedback loop back to the environment

==== The Spectrum of Autonomy
<the-spectrum-of-autonomy>
- #text(fill: red, weight: "bold")[Definition]: #emph[autonomy] measures
  how many decisions a system makes without a human approving each step
  - Low autonomy: human approves every action
  - High autonomy: human only sets the goal and checks the final result

- #text(fill: blue, weight: "bold")[Remark]: most production systems sit

==== Autonomy Levels: Worked Examples
<autonomy-levels-worked-examples>
- #text(fill: red, weight: "bold")[Scripted responder]:
  - A phone tree with fixed prompts and menu choices
  - No model in the loop, no flexibility
- #text(fill: orange, weight: "bold")[Chatbot (no tools)]:
  - An LLM answering questions from a static knowledge base
  - Flexible language, zero ability to act
- #text(fill: green, weight: "bold")[Tool-augmented assistant]:
  - An LLM that can call a calculator or search API
  - A human reviews and triggers each call
- #text(fill: teal, weight: "bold")[Single-step agent]
  - An LLM that picks #emph[one] tool call per user request and executes
    it directly (e.g., #emph["send this email"];)
- #text(fill: rgb("#00FFFF"), weight: "bold")[Multi-step autonomous agent]
  - An LLM that plans and executes a chain of actions toward a goal,
    re-planning after each observation
  - E.g., a coding agent that edits, tests, and fixes its own code
    across many iterations

==== Human-in-the-Loop vs.~Full Autonomy
<human-in-the-loop-vs.-full-autonomy>
- #text(fill: red, weight: "bold")[Human-in-the-loop]
  - #emph[Pros]
    - Catches errors before they have real-world consequences
    - Easier to audit and assign accountability
    - Required in high-stakes domains (e.g., medical, financial, legal
      actions)
  - #emph[Cons]
    - Does not scale: a human must be available for every approval
    - Slows down tasks that need many quick steps (e.g., debugging
      loops)
- #text(fill: blue, weight: "bold")[Full-autonomy]
  - #emph[Pros]
    - Scales to long-horizon tasks no human has time to supervise step
      by step
    - Can react and re-plan faster than a human reviewer
  - #emph[Cons]
    - Errors compound silently across many unsupervised steps
    - Requires strong verification and safety mechanisms before it can
      be trusted

==== The Perceive-Plan-Act Loop: Overview
<the-perceive-plan-act-loop-overview>
- #text(fill: red, weight: "bold")[Definition]: the
  #emph[perceive-plan-act loop] is the control cycle that turns a static
  model into an agent
  - #emph[Perceive];: read the current observation from the environment
  - #emph[Plan];: reason about what to do next, given the goal and
    history
  - #emph[Act];: execute the chosen action, which changes the
    environment
- #text(fill: blue, weight: "bold")[Key idea]: the loop runs until a
  termination condition is met, e.g.,
  - Goal reached
  - Step budget exhausted
  - The agent decides to stop

==== Perceive: Observations and State
<perceive-observations-and-state>
- #text(fill: red, weight: "bold")[Definition]: an #emph[observation] is
  whatever information the environment returns after an action, or at
  the start of an episode
  - E.g., a web page's HTML, a file's contents, a tool's JSON response,
    an error message
- #text(fill: green, weight: "bold")[Problem]: raw observations are
  often too large or noisy to feed directly into the model's context
  window, e.g.,
  - A full HTML page can be tens of thousands of tokens
  - A directory listing can contain irrelevant files
- #text(fill: blue, weight: "bold")[Solution]: agents typically
  #emph[filter] or #emph[summarize] observations before reasoning over
  them
  - E.g., extract only clickable elements from a web page
  - E.g., truncate a log to the last error and surrounding lines

==== Plan: Reasoning About the Next Action
<plan-reasoning-about-the-next-action>
- #text(fill: red, weight: "bold")[Definition]: #emph[planning] is the
  step where the agent decides which action to take next, given the
  goal, the history, and the latest observation

- #text(fill: green, weight: "bold")[(Naive) Solution]: pick the single
  action that looks best given only the current observation

  - Cons: ignores long-term consequences, easily gets stuck in loops

- #text(fill: blue, weight: "bold")[Solution]: interleave explicit
  reasoning with action selection

  - Generate a short chain of thought about the state of the task
  - Use that reasoning to choose the next action, not just the next
    token

- #text(fill: rgb("#8B00FF"), weight: "bold")[Example]: before clicking
  "submit" on a form, the agent reasons #emph["have I filled in all
  required fields? Let me check the last observation"]

==== Act: Executing in the Environment
<act-executing-in-the-environment>
- #text(fill: red, weight: "bold")[Definition]: an #emph[action] is a
  discrete operation the agent can invoke that changes the environment
  or queries it for new information
  - E.g., #text(fill: blue)[`click(element_id)`],
    #text(fill: blue)[`run_tests()`],
    #text(fill: blue)[`search(query)`],
    #text(fill: blue)[`write_file(path, content)`]
- #text(fill: green, weight: "bold")[Remark]: actions are typically
  constrained to a fixed #emph[action space]
  - The agent can only invoke the operations exposed to it
  - This constraint is what makes agent behavior auditable and
    controllable
- #text(fill: blue, weight: "bold")[Example]: a coding agent's action
  space might be limited to #text(fill: blue)[`read_file`],
  #text(fill: blue)[`edit_file`], #text(fill: blue)[`run_command`], and
  #text(fill: blue)[`finish`]

==== Closing the Loop: Feedback and Iteration
<closing-the-loop-feedback-and-iteration>
- #text(fill: red, weight: "bold")[Key idea]: the result of
  #text(fill: blue)[`Act`] becomes the next
  #text(fill: blue)[`Perceive`], which is what distinguishes an agent
  from a one-shot tool call
  - A single tool call answers one question
  - A loop lets the agent #emph[notice] that an action failed and try
    something else
- #text(fill: green, weight: "bold")[Example]: an agent
  - runs a test suite (#text(fill: blue)[`Act`])
  - observes a failing test (#text(fill: blue)[`Perceive`])
  - reasons about the cause (#text(fill: blue)[`Plan`])
  - edits the code (#text(fill: blue)[`Act`] again)
- #text(fill: blue, weight: "bold")[Limitations]:
  - Loops can run indefinitely without a stopping condition or step
    budget
  - Errors early in the loop can compound if the agent does not detect
    them

==== Preview: ReAct and the Loop in Practice
<preview-react-and-the-loop-in-practice>
- #text(fill: red, weight: "bold")[Key idea]: #emph[ReAct] (Yao et al.,
  2022) is the canonical instance of the perceive-plan-act loop
  expressed as a single text trace
  - Interleaves reasoning traces (#text(fill: blue)[`Thought`]) with
    actions (#text(fill: blue)[`Action`]) and their results
    (#text(fill: blue)[`Observation`])
  - #text(fill: blue)[`Thought`] $arrow.r$ #text(fill: blue)[`Action`]
    $arrow.r$ #text(fill: blue)[`Observation`] $arrow.r$
    #text(fill: blue)[`Thought`] $arrow.r$ …
  - The reasoning explains #emph[why] an action was chosen; the
    observation grounds the next thought in what actually happened
- #text(fill: blue, weight: "bold")[Remark]: ReAct is covered in detail
  in Lesson 16.3 (motivation, trace, worked example, and comparison to
  reason-only and act-only methods)

==== What Is a Tool? Definition
<what-is-a-tool-definition>
- #text(fill: red, weight: "bold")[Definition]: a #emph[tool] is a
  function with a well-defined interface

  ```
  (name, input schema, output schema)
  ```

  that the agent can invoke to affect or query something outside its own
  context window

- Aka:

  - "Function" (when exposed via function calling)
  - "Action" (when described from the agent's point of view)

- #text(fill: blue, weight: "bold")[Example tools]:

  - #text(fill: blue)[`search(query: str) -> List[Result]`]
  - #text(fill: blue)[`run_python(code: str) -> str`]
  - #text(fill: blue)[`send_email(to: str, subject: str, body: str) -> bool`]

==== Tool Use: From Function Calls to APIs
<tool-use-from-function-calls-to-apis>
- #text(fill: red, weight: "bold")[(Naive) Solution]:
  - Ask the model to output free-form text describing what it wants to
    do
  - Parse it with regular expressions
  - #emph[Cons];: brittle, ambiguous, breaks whenever the model's
    phrasing shifts
- #text(fill: green, weight: "bold")[Solution]:
  - Expose tools as typed schemas
    #text(fill: blue)[`(name, parameters, types)`]
  - Have the agent emit a structured call (e.g., JSON) that matches the
    schema
  - The runtime
    - Validates the call
    - Executes the underlying function
    - Returns the result as the next observation
- #text(fill: blue, weight: "bold")[Intuition]: same idea as a
  programming-language function signature, applied to model outputs
  instead of source code

==== Environment: Definition
<environment-definition>
- #text(fill: red, weight: "bold")[Definition]: an #emph[environment] is
  everything external to the agent's controller that defines the state,
  the available observations, and the effect of each action
  - The environment owns the "ground truth": what is actually true after
    an action is executed
- #text(fill: blue, weight: "bold")[Example]:
  - In a web agent, the environment is the live web page (DOM, network
    responses)
  - In a coding agent, it is the file system plus a shell

==== Types of Environments: A Taxonomy
<types-of-environments-a-taxonomy>
- #text(fill: red, weight: "bold")[Simulated environments]: sandboxed,
  resettable, often used for training and evaluation
  - E.g., a gridworld, a simulated browser, a mock API
- #text(fill: green, weight: "bold")[Web environments]: real or scripted
  web pages reachable via a browser
  - E.g., #text(fill: blue)[`WebShop`] (Yao et al., 2022), an e-commerce
    site for benchmarking shopping agents
- #text(fill: blue, weight: "bold")[Operating-system environments]: a
  shell, file system, and installed programs
  - E.g., a sandboxed Linux container for a coding agent
- #text(fill: rgb("#8B00FF"), weight: "bold")[Physical / robotic environments]:
  the real world, sensed via cameras and other sensors, acted on via
  actuators
  - Highest stakes: actions are not easily reversible

==== Observations: What the Agent Sees
<observations-what-the-agent-sees>
- #text(fill: red, weight: "bold")[Definition]: the #emph[observation
  function] maps the environment's true state to what the agent is
  actually shown
  - The agent never sees the full state directly; it sees a (possibly
    partial, possibly noisy) observation of it
- #text(fill: green, weight: "bold")[Problem]: partial observability
  means the agent must sometimes act under uncertainty about the true
  state
  - E.g., a web agent does not know if a button click triggered a
    background request until the next page load
- #text(fill: blue, weight: "bold")[Example]: a coding agent's
  observation after #text(fill: blue)[`run_tests()`] is the captured
  stdout/stderr, not the full internal state of the interpreter

==== The Grounding Problem: Definition
<the-grounding-problem-definition>
- #text(fill: red, weight: "bold")[Definition]: #emph[grounding] is the
  problem of connecting a model's internal representation of a task to
  concrete, executable actions in a real environment
  - Aka "symbol grounding" in the older AI literature
- #text(fill: green, weight: "bold")[Problem]: an LLM's output is just
  text
  - Saying #emph["I will click the 'Buy' button"] does not, by itself,
    click anything
  - Without grounding, language and action are disconnected
- #text(fill: blue, weight: "bold")[Question]: how do we turn a token
  sequence into a verifiable change in the world?

==== From Tokens to Actions: Action Spaces
<from-tokens-to-actions-action-spaces>
- #text(fill: red, weight: "bold")[(Naive) Solution]: let the model
  generate free-form natural-language instructions and have a human or a
  separate program interpret them
  - Cons: ambiguous, slow, does not scale to autonomous operation
- #text(fill: green, weight: "bold")[Solution]: define a finite, typed
  #emph[action space] that the model's output is constrained to, and map
  each action deterministically to an effect in the environment
  - E.g., $a in {$#text(fill: blue)[`click(id)`],
    #text(fill: blue)[`type(id, text)`],
    #text(fill: blue)[`scroll(direction)`]$}$
  - The mapping from action to effect is owned by the environment, not
    the model
- #text(fill: blue, weight: "bold")[Remark]:
  - Constraining the action space is also a safety mechanism
  - The agent literally cannot take an action outside the defined set

==== Grounding via Tool Schemas and APIs
<grounding-via-tool-schemas-and-apis>
- #text(fill: red, weight: "bold")[Definition]: a #emph[tool schema]
  grounds language by giving every action a fixed name, typed arguments,
  and a documented effect

  - The model's job is reduced to: pick a tool, fill in valid arguments
  - The schema, not the model's prose, determines what actually happens

- #text(fill: green, weight: "bold")[Example]: the schema
  #text(fill: blue)[`move_file(src: str, dst: str) -> bool`] grounds the
  phrase #emph["move the report to the archive folder"] into a single,
  unambiguous, executable call

- #text(fill: blue, weight: "bold")[Key idea]: good grounding turns "the
  model intends to act" into "the model selects from a closed,
  verifiable set of effects"

==== Example: Grounding in WebShop

  purchase a product matching a natural-language instruction
  - Action space: #text(fill: blue)[`search(query)`],
    #text(fill: blue)[`click(button_or_link)`], each mapping to a
    deterministic page transition in the simulator
- #text(fill: green, weight: "bold")[Why this matters]:
  - Grounding does not require a real browser or real money
  - A faithful, constrained simulation is enough to train and evaluate
    grounded agents

  action space, and findings are covered in detail in Lesson 16.3

==== Dimensions of an Agentic Taxonomy
<dimensions-of-an-agentic-taxonomy>
- #text(fill: red, weight: "bold")[Goal]: classify agentic systems along
  independent axes so that two agents can be compared precisely

- #text(fill: blue, weight: "bold")[Four useful dimensions]:

  + #emph[Control];: reactive vs.~deliberative vs.~hybrid
  + #emph[Cardinality];: single-agent vs.~multi-agent
  + #emph[Environment];: simulated, web, operating system, physical
  + #emph[Autonomy];: human-in-the-loop vs.~fully autonomous

==== Reactive vs.~Deliberative Agents
<reactive-vs.-deliberative-agents>
- #text(fill: red, weight: "bold")[Reactive agents]: map the current
  observation directly to an action, with little or no explicit
  lookahead
  - #emph[Pros];: fast, simple, cheap per step
  - #emph[Cons];: prone to local mistakes, no long-horizon planning
- #text(fill: green, weight: "bold")[Deliberative agents]: maintain an
  internal plan and reason about future states before acting
  - #emph[Pros];: better at long-horizon, multi-step tasks
  - #emph[Cons];: more expensive per step, planning can itself be wrong
- #text(fill: blue, weight: "bold")[Hybrid agents]: deliberate to form a
  plan, then react quickly within that plan, replanning when
  observations diverge from expectations
  - This is the pattern used by most practical LLM agents today (e.g.,
    ReAct)

==== Single-Agent vs.~Multi-Agent Systems
<single-agent-vs.-multi-agent-systems>
- #text(fill: red, weight: "bold")[Single-agent systems]: one controller
  perceives, plans, and acts
  - Simpler to reason about and debug
  - Bottlenecked by that one controller's context and capabilities
- #text(fill: blue, weight: "bold")[Multi-agent systems]: several
  agents, each with its own role, interact to solve a task
  - E.g., a "planner" agent delegates subtasks to "worker" agents
  - E.g., agents negotiate and critique each other's outputs

==== What Is an Agentic AI? Summary and Open Questions
<what-is-an-agentic-ai-summary-and-open-questions>
- #text(fill: red, weight: "bold")[Key takeaways]:
  - An #emph[agentic AI] perceives, plans, and acts toward a goal, in a
    loop, with limited human supervision
  - Autonomy is a spectrum, from scripted responders to fully autonomous
    multi-step agents
  - The perceive-plan-act loop, closed through tools and observations,
    is what turns a static language model into an agent
  - Grounding connects language to executable, verifiable actions via
    typed tool schemas and constrained action spaces
  - Agentic systems can be classified along control, cardinality,
    environment, and autonomy
- #text(fill: blue, weight: "bold")[Open questions]
  - How does the underlying LLM's architecture constrain what an agent
    can reason about?
  - How did the field get from prompting to acting agents like ReAct and
    WebShop?
  - How do we evaluate and trust an agent's behavior before deployment?
