// Styled table with zebra striping, lateral lines, and configurable width.
#let styled-table(headers: (), rows: (), caption: none, col-widths: none, bold-first-col: true, size: 0.8em, width: 80%) = {
  let n = headers.len()
  let widths = if col-widths != none { col-widths } else { (1fr,) * n }

  // Zebra striping: alternate white and darker gray backgrounds on full rows
  let processed-rows = rows.enumerate().map(((idx, row)) => {
    let bg-color = if calc.rem(idx, 2) == 0 { white } else { rgb("#e8e8e8") }
    if bold-first-col {
      (
        table.cell(fill: bg-color, text(fill: black, weight: "bold", row.at(0))),
        ..row.slice(1).map(cell => table.cell(fill: bg-color, text(fill: rgb("#555555"), cell)))
      )
    } else {
      row.map(cell => table.cell(fill: bg-color, text(fill: rgb("#555555"), cell)))
    }
  })

  text(size: size,
    figure(
      align(center,
        block(width: width,
          table(
            columns: widths,
            align: (left,) * n,
            stroke: none,
            table.vline(x: 0, stroke: 2pt),
            table.hline(stroke: 2pt),
            table.header(
              ..headers.map(h => table.cell(fill: black, text(fill: white, weight: "bold", h)))
            ),
            table.hline(stroke: 1.5pt),
            ..processed-rows.flatten(),
            table.hline(stroke: 2pt),
            table.vline(x: n, stroke: 2pt),
          )
        )
      ),
      kind: table,
      caption: caption,
    )
  )
}

=== Simple Is Better
<simple-is-better>
==== Occam's Razor
<occams-razor>
- #text(fill: black, weight: "bold")[Simple is better]
  - #emph["The simplest model that fits the data is also the most
    plausible"] (Occam)

  - #emph["An explanation of the data should be as simple as possible,
    but not simpler"] (Einstein?)
- Corollary:
  - Trim the model to the bare minimum necessary to explain the data
- What does #text(fill: black, weight: "bold")[simple] mean?
  - A model is simple when it is one of few possible objects
- What does #text(fill: black, weight: "bold")[better] mean?
  - A model is better means better out of sample performance
- #text(fill: black, weight: "bold")[Why it's true];?
  - Less likely to fit a given data by coincidence
  - An event is more significant if it is unlikely (formalized in terms
    entropy)

==== What is a "simple model"?
<what-is-a-simple-model>
- An object is #text(fill: black, weight: "bold")[simple] when it is one of few possible objects

- #text(fill: black, weight: "bold")[Examples];:

  - Polynomial of order 2 is simpler than order 17
    - More polynomials of order 17 than order 2, though both are
      infinite sets
  - SVM (Support Vector Machine) characteristics:
    - Separating hyperplane appears wiggly, but defined by few support
      vectors

- #text(fill: black, weight: "bold")[Measures of complexity]

  - Complexity of a single hypothesis $h$
    - E.g., polynomial order, MDL (describe hypothesis in bits),
      Kolmogorov complexity
  - Complexity of a hypothesis set $cal(H)$
    - E.g., VC dimension of the model
  - Complexity of $h$ and $cal(H)$ related by counting:
    - If you need $l$ bits to specify $h$, then $h$ is one of $2^l$
      elements of set $cal(H)$

==== Model Soundness
<model-soundness>
- #text(fill: black, weight: "bold")[Model should tell a story]
  - You cannot blindly accept results of modeling
  - Ask: #emph["What criticisms would you give if the model was
    presented for the first time?"]
- #text(fill: black, weight: "bold")[Benchmark models];: compute performance if model outputs:
  - Always 0 or 1
    - E.g., long-only model for stock predictions
  - Random results
    - E.g., bootstrap of null hypothesis "no prediction power"
- #text(fill: black, weight: "bold")[Perfect fit can mean nothing];, e.g.,
  - Get 2 data points on a plane
    - Fit data with a linear relationship
    - Perfect fit
  - Means nothing since:
    - Always a line between 2 points
    - Data cannot falsify hypothesis
  - The model (line) is too complex for data set (only 2 points)

==== Sampling Bias (1/2)
<sampling-bias-12>
- #text(fill: black, weight: "bold")[Sampling bias] occurs when data is not representative of the
  intended population
  - Biased sampling leads to biased outcomes
  - Model views world through training data
  - Hoeffding's hypothesis: training and testing distributions are the
    same
- #text(fill: black, weight: "bold")[Causes of Sampling Bias]
  - #emph[Non-random sampling];: Favors certain outcomes or groups
  - #emph[Undercoverage];: Inadequate representation of some population
    members
  - #emph[Survivorship bias];: Includes only successful subjects
  - #emph[Self-selection bias];: Participants choose to participate,
    introducing bias
- #text(fill: black, weight: "bold")[Consequences]
  - Systematic errors distort relationships or predictions
  - Models trained on biased samples perform poorly on real-world data
  - Leads to incorrect or unfair decisions

==== Sampling Bias (2/2)
<sampling-bias-22>
- #text(fill: black, weight: "bold")[Examples]
  - Training facial recognition on lighter-skinned faces reduces
    accuracy on darker-skinned faces
  - Predicting income using data only from employed individuals omits
    unemployed people
- #text(fill: black, weight: "bold")[Mitigation]
  - Compare sample statistics with population statistics
  - Use stratified sampling or resampling to balance data
  - Apply re-weighting or bias correction techniques
  - If data points have zero probability ($Pr = 0$), no remedies
    possible

==== Data Snooping (1/2)
<data-snooping-12>
- #text(fill: black, weight: "bold")[Data snooping] occurs when test set information improperly
  influences model-building

- #text(fill: black, weight: "bold")[Typical Sources]

  - #emph[Train-test contamination];: Test data leaks into training
    - E.g., Using test data during feature engineering, model selection,
      or tuning
  - #emph[Multiple hypothesis testing];: Trying many models inflates
    performance

- #text(fill: black, weight: "bold")[Consequences]

  - Overly optimistic evaluations
  - Models perform well in validation but fail on unseen data

- #text(fill: black, weight: "bold")[Why It's Dangerous]

  - Misleading results
  - False confidence in model quality
  - Common pitfall in machine learning workflows

==== Data Snooping (2/2)
<data-snooping-22>
- #text(fill: black, weight: "bold")[Examples]
  - Choosing features based on the full dataset before splitting gives
    foresight not present in deployment
  - E.g., demean the entire data and then split in train / test
- #text(fill: black, weight: "bold")[Preventive Strategies]
  - Keep training, validation, and test sets separate
  - Use cross-validation properly
  - Fit preprocessing steps only on training data, then apply to test
    data

==== "Burning the Test Set"
<burning-the-test-set>
- #text(fill: black, weight: "bold")[Problem]
  - Repeated test set use during development leaks into training
  - Overfitting to test data
  - #emph["If you torture the data long enough, it will confess whatever
    you want"] (Coase, 1982)
- #text(fill: black, weight: "bold")[Symptoms]
  - Test accuracy improves; real-world performance stagnates or degrades
  - Model evaluation becomes untrustworthy
- #text(fill: black, weight: "bold")[Solutions]
  - #emph[One-time use principle];: Evaluate on test set once,
    post-tuning
  - #emph[Use a validation set];: For model development and tuning
  - #emph[Statistical adjustments];:
    - Adjust p-values for multiple testing
    - Use Bonferroni or False Discovery Rate corrections
  - #emph[Theoretical tools];:
    - VC dimension reflects learning capacity, including repeated trials
    - Minimum Description Length (MDL) penalizes complex models and
      repeated fitting

==== How to Achieve Out-Of-Sample Fit
<how-to-achieve-out-of-sample-fit>
- #text(fill: black, weight: "bold")[Goal];: Choose an hypothesis $g in cal(H)$ approximates the
  unknown target function $f$
  - What does $g approx f$ mean?
    $ g approx f arrow.l.r.double E_(o u t) \( g \) approx 0 $
- #text(fill: black, weight: "bold")[Solution];:
  - Achieve:
    - Good in-sample performance $E_(i n) \( g \) approx 0$
    - Good generalization $E_(o u t) \( g \) approx E_(i n) \( g \)$
  - Together $arrow.r.double.long$ good out-of-sample performance
    $E_(o u t) \( g \) approx 0$

==== What If Out-Of-Sample Fit Is Poor?
<what-if-out-of-sample-fit-is-poor>
- The model performs well in sample ($E_(i n) approx 0$) but poorly out
  of sample ($E_(o u t) gt.double E_(i n)$)

- #text(fill: black, weight: "bold")[What does it mean?]

  - In-sample performance is optimistic
  - Model is overfitted and fails to generalize

- #text(fill: black, weight: "bold")[What do you do?]

  - Run diagnostics before long-term projects
  - Gain insight on what works/doesn't to improve performance
    - E.g., bias-variance curves and learning curves

- #text(fill: black, weight: "bold")[How to fix?]

  + Training data
    - Get more training data $arrow.l.r.double$ fixes high variance
  + Features
    - Remove features $arrow.l.r.double$ fixes high variance
    - Add features $arrow.l.r.double$ fixes high bias
    - Add derived features (e.g., polynomial features)
      $arrow.l.r.double$ fixes high bias
  + Regularization
    - Decrease regularization $lambda$ $arrow.l.r.double$ fixes high
      bias
    - Increase regularization $lambda$ $arrow.l.r.double$ fixes high
      variance

==== Why Using a Lot of Data?
<why-using-a-lot-of-data>
- #text(fill: black, weight: "bold")[Several studies] show that:
  - Different algorithms/models have remarkably similar performance
  - Increasing training set improves performance
- #text(fill: black, weight: "bold")[Consequence]
  - High capacity model + massive training set = good performance
- #text(fill: black, weight: "bold")[Why]
  - Using a high capacity model with many parameters (e.g., neural
    network) $ E_(i n) approx 0 $ due to low bias (and high variance)
  - A massive data set helps avoid overfitting
    $ E_(o u t) approx E_(i n) $
  - These two conditions together
    $ E_(o u t) approx E_(i n) approx 0 arrow.r.double.long E_(o u t) approx 0 $

==== Why We Do Things?
<why-we-do-things>
- #text(fill: black, weight: "bold")[Always, always, always:]
  - Understand the purpose of the task
    - Ask: #emph["Why are we doing something?"]
  - Clarify goals and outcomes of the task
    - Ask: #emph["What do we hope to determine by performing the task?"]
  - Think about actions with the bigger picture in mind
  - Avoid going through the motions
  - Prioritize tasks by importance and impact
- E.g., when conducting a customer survey:
  - Q: #emph["Why is the feedback being collected?"]
    - A: To improve product features and customer service
  - Q: #emph["What is the desired outcome?"]
    - A: To identify areas for improvement and innovation
- E.g., before starting a marketing campaign:
  - Q: #emph["Why is this campaign run?"]
    - A: To increase brand awareness or drive sales
  - Q: #emph["What are the specific goals?"]
    - A: Set target number of new leads or click-through rates

==== Summary of the Results, Next Steps
<summary-of-the-results-next-steps>
- #text(fill: black, weight: "bold")[Always have a summary of results]
  - High-level map of discoveries
    - E.g., "smoothing model coefficients helps"
  - Highlight major findings
  - Interpret results
    - E.g., #emph["Increase in sales likely due to new marketing
      strategy."]
  - Conclusions
    - Summarize data suggestions or confirmations
    - E.g., #emph["Hypothesis that user engagement increases retention
      is supported"]
- #text(fill: black, weight: "bold")[Always have a reference to detailed results]
  - Provide quick insights before details
- #text(fill: black, weight: "bold")[Always have next steps]
  - What do you expect to happen?
    - Like thinking $n$ moves ahead in chess
  - E.g., #emph["Next, conduct detailed analysis on demographics
    contributing most to sales growth"]
    - Outline potential experiments or analyses to validate findings
      further

==== Example: Spam Filter Classification
<example-spam-filter-classification>
- You use $N = 5$ words in an email to distinguish spam / non-spam
  emails using logistic regression
  - Words are #text(fill: blue)[buy], #text(fill: blue)[now],
    #text(fill: blue)[deal], #text(fill: blue)[discount],
    #text(fill: blue)[your name]
- #text(fill: black, weight: "bold")[Goal];: improve classifier performance
  + #text(fill: black, weight: "bold")[Collect more data]
    - Honeypot project: fake email account to collect spam
  + #text(fill: black, weight: "bold")[Use better features]
    - Email routing info (spammers use unusual accounts, mask emails as
      legitimate)
  + #text(fill: black, weight: "bold")[Use better features from message body]
  + #text(fill: black, weight: "bold")[Detect intentional misspellings]
    - Spammers use misspelled words (e.g., #text(fill: blue)[w4tch] for
      #text(fill: blue)[watch])
    - Use stemming software

==== Right and Wrong Approach to Research
<right-and-wrong-approach-to-research>
- It is not clear how to prioritize the different possible tasks

- #text(fill: black, weight: "bold")[Bad]

  + Use gut feeling to choose a task
  + Complete task
  + Re-evaluate performance

- #text(fill: black, weight: "bold")[Good]

  + Build a simple algorithm
    - Within 1 day
  + Set up performance evaluation
    - Single number and bounds to improve
    - Use cross-validation
  + Set up diagnostic tools
    - Compute learning and bias-variance curves
    - Understand issues before fixing (avoid premature optimization)
  + Review misclassified emails manually
    - Identify features to improve performance
    - E.g., what are types of misclassified emails?

- Sometimes you just need to try approaches to see if they work

  - E.g., use stemming software to equate words
