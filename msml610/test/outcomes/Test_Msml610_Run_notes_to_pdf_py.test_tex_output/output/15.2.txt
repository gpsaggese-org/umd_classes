\item
  Neural-Symbolic AI: The Integration Problem
\item
  \textbf{Motivation}: Classical AI excels at structured reasoning; deep
  learning excels at pattern recognition

  \begin{itemize}
  \tightlist
  \item
    Classical symbolic systems: rigid, interpretable, struggle with
    perception
  \item
    Neural networks: flexible, learn from data, opaque reasoning
  \item
    Gap: how to combine strengths of both?
  \end{itemize}
\item
  \textbf{Goal}: Create decision-making systems that combine

  \begin{itemize}
  \tightlist
  \item
    Learned representations from data (neural)
  \item
    Structured planning and reasoning (symbolic)
  \end{itemize}
\item
  \textbf{Question}: Can we use neural networks to enhance classical
  planning algorithms like A*?
\item
  \textbf{Key insight}: Neural-symbolic integration is not about
  replacing one with the other---it's about orchestrating them
  synergistically
\item
  The Four Pillars of Neural-Symbolic Decision Making
\item
  \textbf{Pillar 1: Learning Dynamics}: Capture planning algorithm
  behavior via neural models

  \begin{itemize}
  \tightlist
  \item
    \emph{Bootstrapping Search Dynamics} (Beyond A*)
  \end{itemize}
\item
  \textbf{Pillar 2: Dual-Process Reasoning}: Fast intuition + slow
  deliberation

  \begin{itemize}
  \tightlist
  \item
    \emph{Dualformer} (fast heuristics, slow reasoning traces)
  \end{itemize}
\item
  \textbf{Pillar 3: Algebraic Abstraction}: Compose optimizers as

  \begin{itemize}
  \tightlist
  \item
    \emph{Composing Global Optimizers} (functional composition of

\item
  Beyond A*: Problem Setup
\item
  \textbf{Classical A* Planning}: \(f(n) = g(n) + h(n)\)

  \begin{itemize}
  \tightlist
  \item
    \(g(n)\) = cost to reach node \(n\)
  \item
    \(h(n)\) = heuristic estimate to goal
  \item
    Greedy: expand node with lowest \(f(n)\)
  \end{itemize}
\item
  \textbf{The Core Limitation}: Heuristics are hand-crafted

  \begin{itemize}
  \tightlist
  \item
    Admissible heuristics (underestimate true cost) guarantee optimality
    but may be weak
  \item
    Informed heuristics are domain-specific, not generalizable
  \end{itemize}
\item
  \textbf{Key Question}: Can we learn \(h(n)\) from data instead of
  designing it?
\item
  \textbf{Naive Approach}: Train neural network as heuristic function
  \(h_\theta(n) \approx h^*(n)\)

  \begin{itemize}
  \tightlist
  \item
    Problem: Requires extensive labeled data on \((n, h^*(n))\) pairs
  \item
    Problem: No guarantee on admissibility; may overestimate and miss
    optimal solutions
  \end{itemize}
\item
  Beyond A*: Search Dynamics Bootstrapping (Core Idea)
\item
  \textbf{Central Insight}: Don't just learn heuristics---learn the
  \emph{dynamics} of how A* explores

  \begin{itemize}
  \tightlist
  \item
    Observation: The \emph{sequence} of nodes A* expands encodes rich
    planning information
  \item
    Dynamics: How does A* decide which node to expand next?
  \end{itemize}
\item
  \textbf{Bootstrapping Strategy}:

  \begin{enumerate}
  \tightlist
  \item
    Run classical A* with hand-crafted heuristic on training problems
  \item
    Record the \emph{search trajectory}: sequence of expanded nodes
    \((n_1, n_2, ..., n_T)\)
  \item
    Train transformer to predict the next node to expand from partial
    trajectory
  \item
    Use learned transformer as an \emph{enhanced} heuristic for new
    instances
  \end{enumerate}
\item
  \textbf{Why Transformers?}

  \begin{itemize}
  \tightlist
  \item
    Attention mechanism captures dependencies between nodes in search
    trajectory
  \item
    Can learn patterns in \emph{when} to expand nodes based on path
    structure
  \item
    Transferable: trained on one domain, generalizes to similar
    instances
  \end{itemize}
\item
  \textbf{Mathematical Formulation}:

  \[
  \Pr(\text{expand } n_t | n_1, ..., n_{t-1})
  = \text{Transformer}(n_1, ..., n_{t-1})
  \]
\item
  Beyond A*: Ensuring Guarantees
\item
  \textbf{Problem with Direct Learning}: Learned heuristics may violate
  admissibility

  \begin{itemize}
  \tightlist
  \item
    If \(h_\theta(n) > h^*(n)\), A* may miss optimal solutions
  \end{itemize}
\item
  \textbf{Solution: Admissibility-Aware Training}

  \begin{itemize}
  \tightlist
  \item
    Use the learned transformer not as a replacement heuristic, but as a
    \emph{policy}
  \item
    At each step, the transformer suggests which node to expand
  \item
    Only accept suggestion if it maintains admissibility constraints
  \end{itemize}
\item
  \textbf{Hybrid Approach}:

  \begin{itemize}
  \tightlist
  \item
    Transformer learns to imitate A* behavior on training set
  \item
    On new instances, use transformer to guide search (faster
    exploration)
  \item
    Fall back to classical A* guarantees if needed
  \end{itemize}
\item
  \textbf{Empirical Results}:

  \begin{itemize}
  \tightlist
  \item
    Faster convergence on learned domains
  \item
    Maintains solution quality of classical A*
  \item
    Generalizes to unseen problem instances
  \end{itemize}
\item
  Beyond A*: Applications and Limitations
\item
  \textbf{Applications}:

  \begin{itemize}
  \tightlist
  \item
    Path planning in robotics
  \item
    Puzzle solving (Sokoban, Rubik's cube)
  \item
    Planning under constraints
  \end{itemize}
\item
  \textbf{Limitations}:

  \begin{itemize}
  \tightlist
  \item
    Requires representative training trajectories
  \item
    Computational cost of training transformer
  \item
    Domain-specific tuning needed for new problem classes
  \end{itemize}
\item
  \textbf{Key Takeaway}: Neural networks can learn and enhance classical
  algorithms by capturing algorithmic \emph{dynamics} rather than just
  mimicking outputs
\end{itemize}

\item
  Dualformer: The Dual-Process Reasoning Framework
\item
  \textbf{Cognitive Science Inspiration}: Humans solve problems via two
  systems

  \begin{itemize}
  \tightlist
  \item
    \emph{System 1 (Fast)}: Quick intuition, heuristic reasoning
  \item
    \emph{System 2 (Slow)}: Deliberate, step-by-step verification
  \item
    Both are necessary: speed for time-critical decisions, accuracy for
    complex reasoning
  \end{itemize}
\item
  \textbf{Question}: Can neural networks also learn to switch between
  fast intuition and slow deliberation?
\item
  \textbf{Dualformer Architecture}:

  \begin{itemize}
  \tightlist
  \item
    \emph{Fast Path}: Quick neural heuristic (learned directly)
  \item
    \emph{Slow Path}: Iterative reasoning via transformed reasoning
    traces
  \item
    \emph{Control Mechanism}: Learn \emph{when} to use which path
  \end{itemize}
\item
  \textbf{Key Insight}: Don't train a single monolithic model---train
  two complementary pathways with learned control logic
\item
  Dualformer: The Two Reasoning Paths
\item
  \textbf{Fast Path} (Intuitive Heuristic):

  \begin{itemize}
  \tightlist
  \item
    Single-pass neural network \(f_{\text{fast}}(x) \to a\)
  \item
    Extremely fast (milliseconds)
  \item
    Lower accuracy, but sufficient for many decisions
  \item
    Example: Quick classification, fast planning
  \end{itemize}
\item
  \textbf{Slow Path} (Deliberative Reasoning):

  \begin{itemize}
  \tightlist
  \item
    Iterative refinement via reasoning traces \(r_1, r_2, ..., r_T\)
  \item
    Each trace \(r_t\) is an intermediate reasoning step
  \item
    Composed via transformer: \(a = \text{Transformer}(r_1, ..., r_T)\)
  \item
    Much slower, but higher accuracy
  \end{itemize}
\item
  \textbf{Reasoning Traces}: What is \(r_t\)?

  \begin{itemize}
  \tightlist
  \item
    Intermediate representations generated during solving
  \item
    Example: partial solutions in planning, intermediate thoughts in
    reasoning
  \item
    Can be learned or extracted from symbolic solvers
  \end{itemize}
\item
  \textbf{Hybrid Decision}:

  \begin{itemize}
  \tightlist
  \item
    For each input \(x\), predict:

    \begin{itemize}
    \tightlist
    \item
      Should we use fast path? (confidence threshold)
    \item
      Or should we use slow path? (when certainty is low)
    \end{itemize}
  \end{itemize}
\item
  Dualformer: Randomized Training for Robustness
\item
  \textbf{Key Problem}: Training on fixed traces is brittle

  \begin{itemize}
  \tightlist
  \item
    If traces are always the same sequence, model overfits
  \item
    Real solvers produce varied traces depending on initial conditions
  \end{itemize}
\item
  \textbf{Solution: Randomized Reasoning Traces}

  \begin{itemize}
  \tightlist
  \item
    During training, add randomness to trace generation
  \item
    Different runs of same solver produce slightly different traces
  \item
    Force model to be robust to trace variations
  \end{itemize}
\item
  \textbf{Training Objective}:

  \[
  \mathcal{L} = \mathbb{E}_{r \sim \text{RandomTraces}(x)}
    \left[ \ell(f_\text{slow}(r), y) \right] + \text{ControlLoss}
  \]

  \begin{itemize}
  \tightlist
  \item
    \(\text{RandomTraces}(x)\) samples reasoning traces stochastically
  \item
    ControlLoss encourages efficient use of slow path (only when needed)
  \end{itemize}
\item
  \textbf{Why Randomization Helps}:

  \begin{itemize}
  \tightlist
  \item
    Simulates distribution shift (traces vary in practice)
  \item
    Prevents overfitting to specific trace sequences
  \item
    Improves generalization to new problem instances
  \end{itemize}
\item
  Dualformer: Control and Efficiency
\item
  \textbf{Learning When to Deliberate}:

  \begin{itemize}
  \tightlist
  \item
    Fast path produces answer \(a_f\) and confidence \(c_f\)
  \item
    If \(c_f > \tau\) (threshold), return \(a_f\) (save time)
  \item
    Else, invoke slow path (deliberate longer)
  \end{itemize}
\item
  \textbf{Cost-Accuracy Tradeoff}:

  \begin{itemize}
  \tightlist
  \item
    Threshold \(\tau\) controls accuracy vs.~speed
  \item
    High \(\tau\): use fast path often (fast but less accurate)
  \item
    Low \(\tau\): use slow path often (accurate but slow)
  \end{itemize}
\item
  \textbf{Empirical Performance}:

  \begin{itemize}
  \tightlist
  \item
    Achieves fast-path speed on \(\sim 70\%\) of instances
  \item
    Uses slow path for hard instances requiring deliberation
  \item
    Outperforms pure fast or pure slow approaches
  \end{itemize}
\item
  \textbf{Key Takeaway}: Dual-process reasoning via controlled switching
  enables \emph{adaptive} complexity---simple cases resolved quickly,
  hard cases receive extended reasoning
\end{itemize}

  The Composition Problem in Optimization
\item
  \textbf{Motivation}: Real problems often combine multiple objectives

  \begin{itemize}
  \tightlist
  \item
    Optimize cost AND minimize time AND satisfy constraints
  \item
    Different sub-problems have different optimal solvers
  \item
    Need to compose specialized solvers into unified optimizer
  \end{itemize}
\item
  \textbf{Classical Challenge}:

  \begin{itemize}
  \tightlist
  \item
    Monolithic solver: must handle all problem types (slow)
  \item
    Pipeline of solvers: hard to integrate results (inconsistent)
  \item
    Goal: compose solvers as \emph{building blocks} with clear semantics
  \end{itemize}
\item
  \textbf{Algebraic Perspective}: Treat optimizers as algebraic objects

  \begin{itemize}
  \tightlist
  \item
    Solvers form a \emph{semigroup} or \emph{monoid} under composition
  \item
    Can combine via operator overloading and functional composition
  \item
    Get composability ``for free'' via algebraic properties
  \end{itemize}
\item
  \textbf{Question}: What algebraic structure makes sense for
  optimization?
\item
  Algebraic Objects for Optimization
\item
  \textbf{Definition}: A \emph{global optimizer} \(\mathcal{O}\) is a
  map

  \[
  \mathcal{O}: \mathcal{X} \to \mathcal{P}(\mathcal{X})
  \]

  \begin{itemize}
  \tightlist
  \item
    Input: feasible solution set \(\mathcal{X}\)
  \item
    Output: set of \emph{optimal} solutions
    \(\mathcal{P}(\mathcal{X}) \subseteq \mathcal{X}\)
  \end{itemize}
\item
  \textbf{Composition of Optimizers}:

  \begin{itemize}
  \tightlist
  \item
    \(\mathcal{O}_1 \circ \mathcal{O}_2\): Apply \(\mathcal{O}_2\)
    first, then refine with \(\mathcal{O}_1\)
  \item
    \(\mathcal{O}_1 \cap \mathcal{O}_2\): Find solutions satisfying both
  \end{itemize}
\item
  \textbf{Monoid Structure}:

  \begin{itemize}
  \tightlist
  \item
    Identity: trivial optimizer (return all feasible solutions)
  \item
    Associativity:
    \((\mathcal{O}_1 \circ \mathcal{O}_2) \circ \mathcal{O}_3 = \mathcal{O}_1 \circ (\mathcal{O}_2 \circ \mathcal{O}_3)\)
  \item
    Closure: composition of optimizers is an optimizer
  \end{itemize}
\item
  \textbf{Benefits}:

  \begin{itemize}
  \tightlist
  \item
    Modular reasoning about optimizers
  \item
    Reuse existing solvers without modification
  \item
    Automatic composition guarantees correctness
  \end{itemize}
\item
  Algebraic Optimization in Practice
\item
  \textbf{Example: Multi-Objective Knapsack}

  \begin{itemize}
  \tightlist
  \item
    \(\mathcal{O}_1\): maximize value
  \item
    \(\mathcal{O}_2\): minimize weight
  \item
    \(\mathcal{O}_3\): satisfy constraints
  \item
    Composed: \(\mathcal{O}_3 \circ \mathcal{O}_1 \cap \mathcal{O}_2\)
  \end{itemize}
\item
  \textbf{Algebraic Solver Composition}:

  \begin{enumerate}
  \tightlist
  \item
    Encode objective functions as optimization problems
  \item
    Represent solvers as algebraic operations
  \item
    Compose via functional combinators
  \item
    Derive composite solver automatically
  \end{enumerate}
\item
  \textbf{Neural Integration}:

  \begin{itemize}
  \tightlist
  \item
    Learn which composition sequence is optimal via gradient descent
  \item
    Meta-learning: which optimizer order minimizes total solving time?
  \item
    Data-driven composition beats hand-designed pipelines
  \end{itemize}
\item
  \textbf{Complexity Analysis}:

  \begin{itemize}
  \tightlist
  \item
    Composing \(k\) optimizers: \(O(T_1 + T_2 + ... + T_k)\) time
    (sequential)
  \item
    Parallelization possible if optimizers are independent
  \item
    Memory overhead minimal (solvers share solution cache)
  \end{itemize}
\item
  Algebraic Objects: Limitations and Extensions
\item
  \textbf{Limitations}:

  \begin{itemize}
  \tightlist
  \item
    Not all optimization problems fit cleanly into algebraic framework
  \item
    Non-monotonic objectives (e.g., sparsity) harder to compose
  \item
    Theoretical guarantees weaker than problem-specific solvers
  \end{itemize}
\item
  \textbf{Extensions}:

  \begin{itemize}
  \tightlist
  \item
    Extend to \emph{partial orders} instead of total orders
  \item
    Incorporate uncertainty via stochastic optimizers
  \item
    Learn adaptive composition strategies via RL
  \end{itemize}
\item
  \textbf{Key Takeaway}: Algebraic structure enables composable, modular
  optimization---leverage it to build complex solvers from simple,
  verified components
\end{itemize}

\item
  The Combinatorial Optimization Challenge
\item
  \textbf{Definition}: Combinatorial optimization seeks

  \[
  x^* = \arg\max_{x \in \{0,1\}^n} f(x)
  \]

  \begin{itemize}
  \tightlist
  \item
    Discrete variables (binary, integer, categorical)
  \item
    Nonlinear, hard-to-optimize objective \(f\)
  \item
    Example: graph coloring, SAT, scheduling, portfolio optimization
  \end{itemize}
\item
  \textbf{Classical Approaches}:

  \begin{itemize}
  \tightlist
  \item
    Exact solvers (branch-and-bound, ILP): exponential in \(n\), only
    feasible for small \(n\)
  \item
    Heuristics (greedy, genetic algorithms): fast but no guarantees
  \item
    Meta-heuristics (simulated annealing, tabu search): slow but
    occasionally good
  \end{itemize}
\item
  \textbf{Core Challenge}:

  \begin{itemize}
  \tightlist
  \item
    Objective \(f\) is black-box or computationally expensive
  \item
    Gradient-based optimization impossible (discrete variables)
  \item
    Sampling \(f\) is costly
  \end{itemize}
\item
  \textbf{Question}: Can we learn a \emph{cheap-to-optimize}
  approximation of \(f\)?
\item
  SurCo: Surrogate Model Learning
\item
  \textbf{Core Idea}: Learn a \emph{surrogate function} \(\hat{f}\) that

  \begin{itemize}
  \tightlist
  \item
    Is fast to evaluate (milliseconds, not seconds)
  \item
    Correlates strongly with true objective \(f\)
  \item
    Is easy to optimize (e.g., convex or linear)
  \end{itemize}
\item
  \textbf{Surrogate-Based Optimization Loop}:

  \begin{enumerate}
  \tightlist
  \item
    Sample \(f\) at a few initial points
    \(\mathcal{D} = \{(x_i, f(x_i))\}\)
  \item
    Fit surrogate \(\hat{f}\) to \(\mathcal{D}\)
  \item
    Optimize \(\hat{f}\) (cheap) to find promising candidate
    \(x_{\text{cand}}\)
  \item
    Evaluate \(f(x_{\text{cand}})\) (expensive)
  \item
    Add to dataset and repeat
  \end{enumerate}
\item
  \textbf{Why This Matters}:

  \begin{itemize}
  \tightlist
  \item
    If \(\hat{f}\) is good, we find high-quality solutions with far
    fewer \(f\) evaluations
  \item
    Especially valuable when \(f\) is expensive (simulation, real-world
    test, inference)
  \end{itemize}
\item
  SurCo: Linear Surrogates for Discrete Optimization
\item
  \textbf{Why Linear Surrogates?}

  \begin{itemize}
  \tightlist
  \item
    \textbf{Interpretability}: coefficients show variable importance
  \item
    \textbf{Efficiency}: Linear optimization is polynomial (integer
    linear programming via solver)
  \item
    \textbf{Stability}: fewer parameters → less overfitting on small
    samples
  \end{itemize}
\item
  \textbf{Key Challenge}: Learning linear approximation to highly
  nonlinear \(f\)

  \begin{itemize}
  \tightlist
  \item
    Naive regression (minimize \(\|\hat{f}(x) - f(x)\|^2\) over training
    data) produces poor optimizer
  \item
    Regression minimizes pointwise error, not \emph{optimization error}
  \end{itemize}
\item
  \textbf{SurCo Approach: Optimize for Optimization}, not prediction

  \[
  \hat{f}_\text{SurCo}
    = \arg\min_{\hat{f} \in \text{Linear}}
      \mathbb{E}_{f}
      \left[
        \left| f(x^*_{\hat{f}}) - f(x^*_f) \right|
      \right]
  \]

  \begin{itemize}
  \tightlist
  \item
    \(x^*_{\hat{f}}\) = argmax of surrogate
  \item
    \(x^*_f\) = argmax of true function
  \item
    Minimize \emph{optimization loss}, not prediction loss
  \end{itemize}
\item
  \textbf{Why It Works}:

  \begin{itemize}
  \tightlist
  \item
    Focuses learning on high-value region (where optimum is)
  \item
    Ignores prediction error in unimportant regions
  \item
    Often finds near-optimal solutions even with poor pointwise fit
  \end{itemize}
\item
  SurCo: Algorithm and Complexity
\item
  \textbf{Training Algorithm}:

  \begin{enumerate}
  \tightlist
  \item
    Collect training data \(\mathcal{D} = \{(x_i, f(x_i))\}_{i=1}^m\)
    via sampling
  \item
    For each candidate linear model \(\hat{f} \in \mathcal{F}\):

    \begin{itemize}
    \tightlist
    \item
      Optimize \(\hat{f}\) over discrete space:
      \(x_{\hat{f}} = \arg\max_x \hat{f}(x)\)
    \item
      Evaluate true objective:
      \(\text{loss} = f(x^*_{\hat{f}}) - f(x^*_f)\) (or regret)
    \end{itemize}
  \item
    Select \(\hat{f}\) with lowest optimization loss
  \end{enumerate}
\item
  \textbf{Computational Complexity}:

  \begin{itemize}
  \tightlist
  \item
    Training data collection: \(O(m \cdot T_f)\) (sample \(m\) points,
    each cost \(T_f\))
  \item
    Surrogate learning: \(O(m \cdot |\mathcal{F}|)\) (search linear
    model space)
  \item
    Optimization via surrogate: \(O(\text{poly}(n))\) (integer linear
    program)
  \item
    Total: feasible when true objective \(f\) is very expensive
  \end{itemize}
\item
  \textbf{Empirical Results}:

  \begin{itemize}
  \tightlist
  \item
    Achieves near-optimal solutions with \(5\)-\(10\times\) fewer \(f\)
    evaluations than random search
  \item
    Often competitive with problem-specific solvers
  \item
    Generalizes across problem instances
  \end{itemize}
\item
  SurCo: Real-World Applications
\item
  \textbf{Portfolio Optimization}:

  \begin{itemize}
  \tightlist
  \item
    \(f\) = portfolio return (requires simulation or historical
    backtest)
  \item
    SurCo learns linear surrogate of risk-return tradeoff
  \item
    Finds good allocations with few expensive evaluations
  \end{itemize}
\item
  \textbf{Drug Discovery}:

  \begin{itemize}
  \tightlist
  \item
    \(f\) = binding affinity (requires molecular simulation or
    experiment)
  \item
    Surrogate guides molecular search with limited lab evaluations
  \item
    Accelerates discovery pipeline
  \end{itemize}
\item
  \textbf{Hardware Design}:

  \begin{itemize}
  \tightlist
  \item
    \(f\) = chip performance (requires synthesis, simulation, or
    fabrication)
  \item
    Surrogate optimizes design parameters with fewer expensive runs
  \end{itemize}
\item
  \textbf{Key Takeaway}: When objective is expensive, optimize for
  \emph{optimization quality}, not \emph{prediction quality}---learn
  surrogates that find good optima, not surrogates that fit data well
\end{itemize}
\end{frame}
