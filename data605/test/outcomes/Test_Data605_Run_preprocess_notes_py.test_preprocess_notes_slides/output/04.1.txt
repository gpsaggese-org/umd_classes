#### Relational Model: Overview
- Introduced by Ted Codd (late 60's, early 70's)

- **\textcolor{red}{First prototypes}**
  - Ingres Project at Berkeley (1970-1985)
    - Ingres (INteractive Graphics REtrieval System)
    - $\to$ PostgreSQL (=Post Ingres)
  - IBM System R (1970s) $\to$ Oracle, IBM DB2

- **\textcolor{darkgreen}{Contributions from relational data model}**
  - Formal semantics for data operations
  - Data independence: separation of logical and physical data models
  - Declarative query languages (e.g., SQL)
  - Query optimization

- **\textcolor{blue}{Key to commercial success}**

#### Relational Model: Key Definitions
::: columns
:::: {.column width=60%}

- Relational DB is a collection of **\textcolor{red}{tables / relations}**
  - Unique name and schema for each table
  - E.g., \textcolor{blue}{\texttt{instructor}} and \textcolor{blue}{\texttt{course}} relations

- **\textcolor{orange}{Row / tuple / record}**: Represents a relationship among values

- **\textcolor{darkgreen}{Element}**: Corresponds to a **\textcolor{teal}{column / field / attribute}**
  - Atomic elements (e.g., phone number as a single object)
  - \textcolor{blue}{\texttt{NULL}} for unknown or non-existent values

- **\textcolor{cyan}{Schema of a relation}**
  - List of attributes and their domains
  - Like type definition in programming languages
  - E.g., domain of \textcolor{blue}{\texttt{salary}} is integers >= 0

- **\textcolor{blue}{Instance of relation}**
  - Specific instantiation with actual values
  - Changes over time

#### Primary Key
::: columns
:::: {.column width=65%}

- _R_ is a set of attributes of a relation _r_
  - E.g., \textcolor{blue}{\texttt{ID, name, dept\_name, salary}} are attributes of \textcolor{blue}{\texttt{instructor}}

- _K_ is a superkey of _R_ if values for _K_ identify a unique tuple of each
  relation _r(R)_
  - E.g., \textcolor{blue}{\texttt{(ID)}} and \textcolor{blue}{\texttt{(ID, name)}} are superkeys of \textcolor{blue}{\texttt{instructor}}
  - \textcolor{blue}{\texttt{(name)}} is not a superkey of \textcolor{blue}{\texttt{instructor}}

- **\textcolor{red}{Primary key}**: minimal set of attributes that uniquely identify each row
  - Typically small and immutable
  - Would \textcolor{blue}{\texttt{SSN}} be a primary key? Yes and no

- **\textcolor{blue}{Primary key constraint}**: rows can't have the same primary key

#### Foreign Key
::: columns
:::: {.column width=60%}

- **\textcolor{red}{Foreign key}** = primary key of another relation
  - E.g., \textcolor{blue}{\texttt{(ID)}} from \textcolor{blue}{\texttt{student}} in \textcolor{blue}{\texttt{takes}}, \textcolor{blue}{\texttt{advisor}}
  - \textcolor{blue}{\texttt{takes}} is the "referencing relation", has the foreign key
  - \textcolor{blue}{\texttt{student}} is the "referenced relation", has the primary key
  - Shown by an arrow from referencing $\to$ referenced
::::
:::: {.column width=35%}
![](data605/lectures_source/images/lecture_4_1/lec_4_1_slide_10_image_1.png)
::::
:::

- **\textcolor{blue}{Foreign key constraint}**: for each row, the primary key tuple must exist
  - Aka referential integrity constraint
  - If \textcolor{blue}{\texttt{(student101, DATA605)}} is in \textcolor{blue}{\texttt{takes}}, there must be \textcolor{blue}{\texttt{student101}} in
    \textcolor{blue}{\texttt{student}}

- The key referenced as a foreign key must exist as a primary key

#### Relational Algebra: 1/4
::: columns
:::: {.column width=70%}

- **\textcolor{red}{Relation}**: set of tuples

- **\textcolor{orange}{Relational algebra}**: operations on relations producing a new relation
  - Unary: selection, projection, rename
  - Binary: union, set difference, intersection, Cartesian product, join

- **\textcolor{darkgreen}{Selection $\Sigma$}**: select tuples satisfying a predicate
  - E.g., select \textcolor{blue}{\texttt{instructor}} tuples where \textcolor{blue}{\texttt{dept\_name = "Physics"}}

- **\textcolor{teal}{Projection $\pi$}**: return tuples with subset of attributes
  - E.g., project \textcolor{blue}{\texttt{instructor}} tuples with \textcolor{blue}{\texttt{(name, salary)}}

- **\textcolor{cyan}{Set operations}**: union, intersection, set difference
  - Must be compatible (same attributes)

#### Relational Algebra: 2/4

- **\textcolor{red}{Cartesian product}**: combine two relations into a new one
  - \textcolor{blue}{\texttt{instructor}} = \textcolor{blue}{\texttt{(ID, name, dept\_name, salary)}}
  - \textcolor{blue}{\texttt{teaches}} = \textcolor{blue}{\texttt{(ID, course\_id, sec\_id, semester, year)}}

- E.g., \textcolor{blue}{\texttt{instructor}} x \textcolor{blue}{\texttt{teaches}} gives
  \textcolor{blue}{\texttt{(instructor.ID, instructor.name, instructor.dept\_name, teaches.ID, ...)}}

#### Relational Algebra: 3/4

- **\textcolor{red}{Join}**: composition of two operations

  - Selection based on equality between two fields
  - E.g., \textcolor{blue}{\texttt{instructor}} x \textcolor{blue}{\texttt{teaches}} when \textcolor{blue}{\texttt{instructor.ID = teaches.ID}}

#### Relational Algebra: 4/4
::: columns
:::: {.column width=55%}
- **\textcolor{red}{Query}**: combination of relational algebra operations
  - E.g., _"find \textcolor{blue}{\texttt{course\_id}} from table section for fall 2017"_

- **\textcolor{darkgreen}{Assignment}**: assign parts of relational algebra to temporary relation
  variables
  - Write a query as a sequential program
  - E.g., _"find \textcolor{blue}{\texttt{course\_id}} for classes in both fall 2017 and spring 2018"_

- **\textcolor{blue}{Equivalent queries}**: two queries giving the same result on any DB instance
  - Some formulations are more efficient
